# Lightweight runtime：生产容器前后对比

日期：2026-11-01。范围为通用 VPS/Linux/NAS 自部署的运行时优化；所有 App、账户隔离、密码强度和事务语义保留。架构及验收标准见 [工作清单](../worklists/LIGHTWEIGHT_RUNTIME_WORKLIST.md)。

## 结论

- 两组配对的初始空闲 CPU 降低 **83.94% / 83.36%**；操作后空闲 CPU 降低 **76.46% / 78.70%**。初始空闲绝对改善分别为 2.172 / 2.129 个单核百分点，远大于基线重复差 0.033 和候选重复差 0.010，满足预定的重复性要求。
- 单客户端工作集内存中位值降低 **13.80% / 14.42%**，每成功请求 CPU 时间降低 **18.29% / 14.01%**。
- 5 客户端工作集中位值降低 **23.21% / 11.61%**；吞吐下降 **2.75% / 2.98%**。每请求 CPU 时间分别下降 1.40%、上升 2.38%，因此不宣称该负载的单位工作 CPU 效率稳定改善。
- 初始空闲内存仅第一对下降，第二对基本相同；操作后空闲工作集中位值反而增加 **1.64% / 7.39%**。部分采样峰值也未下降，不能泛化为所有场景节省内存或据此降低硬内存上限。
- 四轮 **22,927** 个记录响应均符合预期，包含刻意验证的 401/404；全部附件 SHA-256 校验、双用户隔离、最终数据行数与清理断言通过。
- 两对混合负载吞吐均高于对应基线的 90%；p95 增幅均小于预定的 `max(25% × 基线 p95, 10 ms)` 调查门槛。结论保留约 3% 的 5 客户端吞吐代价，不以降低吞吐掩盖节省。

## 方法与边界

> 登录长尾限制：`candidate-2` 的登录 p95 为 **869.98 ms**，对应基线为 **91.12 ms**，触发了调查门槛。补充 B3/C3 未复现，但原异常原因仍未定位；下文保留原结果、调查证据及性能例外，不将功能成功或一次正常复测视为异常已修复。

- 顺序：`baseline-1 → candidate-1 → candidate-2 → baseline-2`；每轮新容器、新数据卷、新凭据及回环端口，串行运行，正式采集期间无其他构建或测试。
- 宿主 Apple M4/10 核/24 GiB，Docker 29.8.2 的 Linux aarch64/cgroup v2；Engine 报告 10 CPU、12,599,537,664 bytes 内存。服务均为生产镜像：Node 22.23.4、PostgreSQL 17.11、Nginx 1.30.6。宿主压测客户端和 VM/操作系统自身开销不计入服务指标。
- 基线提交：`f6f625c29b8c52ba967d8a3966e651d0a0d815bf`。候选是本批冻结的 runtime/Compose 改动；两个候选源码清单相同，两个基线源码清单相同，四轮 harness 和基础镜像标识相同。
- 每轮主账户含 500 任务、500 笔记、200 资产。第二账户验证空列表、跨账户读/改/删拒绝、附件拒绝、自己的会话撤销；负载结束仍为 500/500/200 行，附件 0。6 个 App 均启用。
- 预置数据和隔离检查后：空闲 60s；1/5 客户端各 60s，每客户端每轮 9 并行读、6 串行 CRUD，轮后等待 1s；成功登录 30s；1/10 MiB 附件上传/下载/hash/删除各 20s、轮后等待 0.5s；最后空闲 60s。5 客户端读阶段最多 45 在途请求，不等于五名真人容量认证。
- 约每秒读取容器累计 CPU 和内存 counters，真实生产健康检查保留。CPU 100% 表示一逻辑核；区间累计 CPU 差除以单调时钟时长，排除阶段边界。CPU/成功请求使用同一采样窗口的请求计数。
- 工作集为容器 `usage - inactive_file`（本次 cgroup v2）；另保留原始 memory charge。这里不是 macOS 进程 RSS，不与前次原生测量计算优化百分比。表中峰值是约 1 秒采样峰值，可能漏掉亚秒峰值。
- 本地 HTTP 无公网 RTT/TLS；主要比较每配置两轮，另有一对诊断复测；未做饱和、长时间泄漏、低内存 OOM/Swap 或其他 VPS CPU 架构容量测试。变化是组合配置的效果，未做每个参数的独立归因。**不声明支持 512 MiB 总内存，也不声明某个最低服务器规格。**

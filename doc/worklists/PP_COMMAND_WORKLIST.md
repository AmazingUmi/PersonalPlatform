# PersonalPlatform server command

## Objective and gap

Expose the accepted deployment manager as `pp update`, `pp status` and `pp resume`, with `pp help` available without deployment privileges. Baseline is clean `2077964` on `codex/deploy-updater`; the existing installer already owns all download, backup, data identity, update and recovery behavior. Its two successful exits currently save only `deploy.sh` in the managed deployment directory.

## Decisions

1. Keep the standalone distribution: generate a small Bash launcher inside `scripts/deploy.sh`; no source checkout, second download or new application release. Map `update` to the existing install-or-update path, `status` to `--status`, and `resume` to `--resume`. `help`/`--help` and no arguments show usage. Unknown commands/options fail before invoking the manager. Update accepts only `--version` and `--bundle-dir`; neither command may override its bound deployment directory, credentials, adoption mode or recovery mode.
2. After a healthy installation, adoption or same-version rerun, save the installer and register an executable `pp` under `/usr/local/bin`. `--command-dir PATH` selects another existing or newly created command directory, including a private non-root directory and isolated test fixtures. Persist its canonical path in `.deploy/command.path`; later full-path reruns reuse it unless explicitly supplied with the same path. Do not edit shell startup files or change PATH. One command directory binds to one deployment.
3. Render the canonical absolute deployment and command paths as quoted Bash literals, with the deployment owner's UID. Run from any working directory and forward argument boundaries, exit status and signals with `exec`. For root-owned deployments, a non-root invocation requests the normal sudo authentication and executes only the saved installer with its bound paths and validated arguments. Other owner mismatches fail with actionable guidance; do not silently promote a non-root deployment to root. Help never invokes sudo or reads private state.
4. Preflight the command directory, target and permissions before downloads, application stop or migration attempts. Refuse symlink/directory targets, unrelated files, another deployment's launcher and modified previously registered launchers. Recognize an existing launcher only by the saved private SHA-256 digest or exact freshly rendered bytes for the same binding (which also closes the publish-before-record interruption window). Retain the digest in `.deploy/command.sha256`; never source/eval these records. Use an owner-checked regular lock in the command directory plus `flock` to serialize registrations across deployment directories. Stage the launcher in that directory and publish atomically.
5. Keep registration outside the database transition: after the application has been accepted and pending state removed, use one shared finalization helper for both successful exits. A rare final launcher-publication or identity-record failure reports clearly that the deployment is healthy and the command registration needs a same-version full-path retry; it must not stop accepted application writers or pretend a migration failed. No second deployment state machine, automatic privilege escalation during installation or automatic data rollback.
6. An existing deployment gains this command by downloading the new pinned installer and rerunning it with the original `--dir`. Existing volumes, configuration, release version, database and matching-backup semantics remain owned by the established manager. Include the self-contained launcher logic automatically in future release bundles through their existing deploy.sh packaging.

## Acceptance and regression matrix

| Area | Evidence |
|---|---|
| Mapping | `help` requires no private access; update/status/resume invoke the correct existing operation; unknown command/flags rejected; exit codes and argument boundaries retained |
| Binding | Non-default deployment/command paths, spaces and shell metacharacters work without code evaluation; cwd and ambient env cannot select another deployment; mismatched owner is refused or requests sudo only for a root-owned deployment |

## Checkpoints and evidence

- Architect proposal and independent reviewer checkpoint: ACCEPTED before implementation. Preflight must concretely require owner-controlled, non-group/other-writable command directory, lock and target; use exclusive staging while holding the command lock. Finalization runs only after pending state has been cleared. Regressions must exercise installer-save failure, launcher-publish failure and publication interrupted before the digest record is updated.
- Review clarification: ownership must cover both command and bound deployment directory ancestors, because an untrusted writable or untrusted-owned parent can rename and replace an otherwise protected leaf or saved installer. Require root/deployment-owner ancestry without group/other write access; trusted sticky temporary ancestors may be accepted only when the protected child also has trusted ownership. Add regressions with unsafe parents and safe leaves before implementing this check. This changes command-file preflight only, not deployment/data transitions.

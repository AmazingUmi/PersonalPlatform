# One-command install and update

## Objective and gap

Provide one standalone Bash script for a public Linux server: first run installs the published paired images, and later runs update the same deployment while preserving users, database rows, attachments, WebDAV keys and private configuration. The server needs Docker Engine, Compose >=2.20, curl and ordinary Linux shell utilities; it must not need a source checkout, host Node/npm/Python/jq, or a compiler.

Baseline: clean `main` at `a346303`, published immutable `v0.1.0`. Existing bundles contain matching digest-pinned images, two Compose files, `release.json`, env template and checksums. Manual download, credentials, update backup and state management are the current gap.

## Architecture decisions

1. Implement `scripts/deploy.sh` as a standalone Bash entry point, distributed through a pinned source-commit URL and included in future release bundles. It can consume the existing `v0.1.0` bundle; do not replace that release, retag its images, or create a new application version only to deliver the script. Document one shell line that downloads the whole script successfully before executing it. Hidden input uses `/dev/tty`, so downloaded execution does not consume a password from the code stream.
2. Default operation is install-or-update for one explicit deployment directory (`--dir`); choose a documented stable default. Accept an explicit stable `--version vMAJOR.MINOR.PATCH`, otherwise resolve GitHub's latest non-prerelease release redirect and pin that exact version for the entire run. Only HTTPS downloads from the official repository/release asset endpoints are accepted. Reject malformed/prerelease versions and downgrades. Re-running the currently active version is an idempotent health/no-op path, not credential regeneration or a destructive restart.
3. Acquire one directory-scoped deployment lock before reading or mutating managed state. Use persistent private state (0700 directories, 0600 env/backup/state files), validated paths, atomically replaced state files and a journal recording source/target version, phase and backup path. Keep immutable release directories, the saved private `.env.release`, and the last accepted release reference distinct. Reject unsafe symlinks and unmanaged nonempty targets. Preserve the last accepted deployment and every recovery artifact on failure; no automatic backup pruning in this batch.
4. Stage downloads outside the active release, validate the external archive checksum, reject archive traversal/absolute paths/link entries/unexpected layout, then validate all required bundle files and internal checksums before use. An explicit local `--bundle-dir` may supply already-downloaded assets for tests/manual asset transfer, with the same validation; registry access is still required for image pulls, so full offline deployment is not promised. Do not add an arbitrary remote mirror flag. Only take the two matching digest-pinned app references from the validated bundle. Do not parse JSON through fragile general-purpose regex, source/eval any downloaded/private env, or execute downloaded configuration as shell. If structured parsing is needed, using the already-pulled application container's Node runtime is acceptable; host Node remains unnecessary.
5. First install generates a strong random database password using the host entropy source; ask for administrator username and password twice with hidden password input and existing backend length constraints. Support a documented noninteractive private-env-file path. Do not accept a password on CLI arguments, print it, put it in public state, or overwrite an existing env with an empty release template. Save custom ports, resource settings, WebDAV origin policy/key and credentials. On updates replace only the paired app image references. Clear conflicting ambient Compose/interpolation variables so saved configuration and the explicit project identity win; preserve only the Docker client context needed to reach the intended daemon.
6. First installation must reject an existing project's containers or data volumes unless explicitly adopting it. Support explicit adoption of an existing release deployment with its real `.env.release` and directory; verify the project labels and actual DB/storage mount identities before takeover. Record the exact project and named volumes, and verify them on each later run. Do not guess by volume suffix, attach unrelated volumes, change a project name to escape a collision, or treat an empty new database as a successful update. More complex/source-build/custom-volume layouts may be refused with precise manual guidance.
7. Complete network/config/tool/version checks and pull the target paired app images before stopping writers. Preserve the existing running database image/settings on routine app updates; do not silently perform a PostgreSQL major upgrade or recreate an unrelated database. Fail if a candidate requires an unsupported DB/topology change. Initial install may pull the release's database service. Existing `127.0.0.1` frontend binding, private backend/DB and Secure cookies remain the defaults. Host Docker installation, DNS, certificates and external HTTPS proxy are separate operator setup.
8. Before a real update, journal the transition, stop frontend and backend (including its scheduler), verify they are stopped, and make a matching backup while the old database remains available. Save a checked DB dump using its PostgreSQL container tools, the complete app-storage archive including `.core/backup.key`, old private env, old bundle/release metadata, actual image/volume identities, and old image's built-in config. Validate archive readability and write a backup-complete marker last. Keep all artifacts private; do not expose credentials through `compose config` output. Use the existing old image or stopped container for storage/config access, with no new helper-image dependency.
9. If staging/pull fails, leave the running application alone. If a backup fails before any target backend can start, retain artifacts and restore only the old services that this run stopped. Immediately before target startup durably mark migration/application as attempted. After that boundary, failure or ambiguous interruption must stop application writers, keep the database/storage and backup, record a persistent failed/pending state, and return nonzero. Never blindly restart an old image against possibly migrated data, reset data, invoke `down -v`, or automatically restore the backup. A documented explicit forward retry (`--resume` or equivalent) must use the journaled target and retained backup; a different version cannot silently replace an unfinished operation. Explain manual matching backup recovery when forward retry is inappropriate.
10. Apply the target with no local build, wait for container health and perform an HTTP readiness check. Atomically mark the target active only after success. Print the version, directory, health and local proxy address, plus the HTTPS prerequisite. Routine update retains account passwords, sessions, DB and attachment bytes. The installer does not log into or change users' WebDAV accounts and makes no new provider-compatibility claim.

- Review-driven amendment: directory locking alone does not serialize different directories targeting the same daemon/project. Add an atomic daemon-scoped empty ownership volume, retaining the first canonical-directory hash and persisted random installation-owner ID. Verify that claim before app mutation and before failure-trap cleanup; keep it on failure. Add real concurrent project-collision and kernel-lock contention/release coverage.
